# Architecture

The launcher is a set of Gradle modules with one rule above all others: **no
engine lives inside an Activity**. An Activity asks for an interface; the only
code that knows what implements it is `AppGraph`. Everything below is written so
that rule is structural rather than a convention someone has to remember.

## 1. Module graph

```
:app                       launcher-ui — 7 screens, service, runtime glue
 ├── :core:map-api             Geo types, MapController, RouteGeometry
 ├── :core:map-engine-maplibre MapLibre renderer, MapPack, StyleBuilder
 ├── :core:place-search        SqlitePlaceSearch, FTS4, VietnameseText
 ├── :core:routing-engine-offline  A* router over the pack's graph.bin
 ├── :core:location-engine     GPS validation, smoothing, bearing filter, snapping
 ├── :core:navigation-core     state machine, guidance, VoiceGuidance
 ├── :core:music-api           Track, PlaybackState, MusicBackend, MediaScanner
 ├── :core:music-engine-local   MediaStore, SQLite library, MediaPlayer, queue
 ├── :core:music-provider-online  (empty shell in this build)
 ├── :core:vehicle-audio-bridge AudioFocus, duck/unduck, media stream
 └── :core:diagnostics         (empty shell in this build)
```

The two empty shells are deliberate and are excluded from anything that would
require behaviour from them. `:app` still lists them as dependencies — that
costs nothing and keeps the wiring in place for the next phase — but no screen
navigates to a screen they would back, and `SettingsActivity` carries no
diagnostics row. See `KNOWN_LIMITATIONS.md`.

Dependency direction is strictly downward. `:core:map-api` knows nothing about
MapLibre; `:core:navigation-core` knows nothing about Android rendering;
`:core:place-search` and `:core:routing-engine-offline` are plain Kotlin over
`java.io` and `android.database` and have no UI types at all. That is what makes
their unit tests runnable on the JVM.

## 2. Ownership and lifetime

| object | owner | lifetime |
|--------|-------|----------|
| `AppGraph` | `Ts8LauncherApp`, exposed as `AppGraph.current` | process |
| `MapView` + `MapLibreMapController` | `MapHost`, one per map screen | the Activity |
| `NavigationController` | `AppGraph`, built lazily | process |
| `LocalMusicBackend` + `MediaPlayer` | `MusicPlaybackService` | service |
| media session | `MusicPlaybackService` via `SessionBuilders` | service |
| `LocationManager` registration | `LocationRuntime`, reference-counted | first acquire → last release |
| `PlaceSearchService` | `AppGraph` | process, dropped on pack change |

The split between *process* and *Activity* is the load-bearing decision:

- The **map** belongs to the Activity because a `MapView` owns a GL surface, and
  a surface must be created and destroyed with the window. Keeping one alive
  behind a task would hold GPU memory for a screen nobody is looking at on a
  device that has very little of it.
- The **navigator** belongs to the process because guidance must survive a
  screen change. Tapping "Âm nhạc" while 200 m from a turn must not cancel the
  instruction the driver is about to reach.
- The **player** belongs to the service because audio must survive Activity
  destruction — including the launcher being recreated while the car is parked
  and the app is in the background.

`AppGraph.invalidatePack()` is the one place that has to respect this ordering.
It closes the search service before the engine it wraps, and shuts the
navigator down because the navigator holds a router over the graph that is about
to be released. Getting that order wrong is a use-after-close that only shows up
as "search stops working" ten minutes later.

## 3. Threading

There are four threads that matter:

| thread | what runs there | why |
|--------|-----------------|-----|
| main | every MapLibre call, every View write, every navigator *delivery* | MapLibre is not thread-safe; a silent hop would reorder camera updates |
| `ts8-io` (2 threads) | search dispatch, media scan, pack reload | one for a running scan, one so search never queues behind it |
| routing executor (owned by `NavigationController`) | route computation, reroute | a 300 ms A* must not block a frame |
| MediaPlayer's internal thread | decoding | not ours |

Every navigator callback is hopped to the main thread exactly once, at the
boundary in `MapActivity` / `HomeActivity`'s listener. Everything past that point
is main-thread code with no further synchronisation.

`LocationRuntime` fans out fixes on the main thread after its engine has
filtered them, so a screen never has to reason about which thread a fix arrived
on.

## 4. Offline contract

Nothing on the map, search, routing or navigation path touches the network.
That is enforced by construction, not by a setting:

- The style document is generated by `StyleBuilder` from `metadata.json` and the
  pack's own glyph/sprite paths. There is no style URL.
- The tile source is `mbtiles://<absolute path>`, served by MapLibre's native
  `MBTilesFileSource`.
- `MapLibreRuntime.configure` disables network access on the `MapLibreMap`, so a
  misconfigured style can only fail — it cannot leak a request.
- Search reads a SQLite file from the pack; routing memory-maps `graph.bin`.

`MapLibre.getInstance(Context)` passes `null` for the API key and never calls
`throwIfApiKeyInvalid`, verified against the 12.0.0 AAR. No key is required,
which is what makes a fully offline pack possible at all.

## 5. Failure is a state

Every engine follows the same shape: a constructor or `open` that returns a
result or null, and a screen that renders the reason. Specifically:

| condition | what the driver sees |
|-----------|----------------------|
| no map pack | the failure text from `MapPack.load`, in the map pane |
| pack present, `places.db` missing | search screen says so once; no fake results |
| pack present, `routing-graph/` missing | navigation tab says "chưa có dữ liệu"; no fake route |
| no GPS fix | "đang tìm tín hiệu"; speed is not shown as 0 |
| empty music library | "chưa phát nhạc" |
| permission denied | the screen that needs it asks, then explains |

There is no demo data anywhere in the app. A blank grid that looks like a map
is worse than a sentence, and the spec's "không dùng dữ liệu demo" is enforced
by having nowhere for demo data to come from.

## 6. What is deliberately not here

- No left menu, on any screen, at any width. Navigation is the bottom bar and
  nothing else (`BaseScreenActivity` is the only place that decides where a nav
  tap goes).
- No Compose, Flutter, React Native or WebView UI. Views and XML only.
- No firmware interaction of any kind. The firmware tree is an asset for a later
  phase and is not read, unpacked or flashed by anything in this repository.
- No automatic takeover of the Home role. The stock launcher is never disabled.
  `HomeActivity` is a Home *candidate* so a person can choose it; it never
  chooses itself (`ADB_INSTALL_AND_RECOVERY.md` §4 and §5).

See `ANDROID_6_COMPATIBILITY.md` for the API-level decisions and
`KNOWN_LIMITATIONS.md` for what this build cannot do.
